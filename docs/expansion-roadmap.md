# 横展開・今後の開発メモ

最終更新: 2026-06-01

## 1. 目的

今回のソフトテニス試合ノートを、今後の開発資産として使う。

候補:

- ピックルボール用の試合記録アプリ
- テニス用の試合記録アプリ
- ソフトテニス用の別アプリ
- 団体戦管理アプリ
- 練習メニュー、課題管理アプリ
- 選手別成長記録アプリ

## 2. 横展開しやすい共通部分

以下は競技が変わっても再利用しやすい。

- スマホファーストの画面設計
- 端末内保存
- オフライン対応
- 記録、分析、履歴の3画面構成
- サマリー画像
- CSV出力
- 検証環境、本番環境の運用
- Markdownによる要件、設計、テスト記録
- GitHub Pages公開

## 3. 競技別に変える部分

以下は競技ごとに変える必要がある。

| 項目 | ソフトテニス | テニス | ピックルボール |
| --- | --- | --- | --- |
| スコア | 4ポイント先取、ファイナル7点 | 15/30/40、ゲーム、セット | 11点先取など |
| サービス | ダブルスの順番、ファイナル2本交替 | サービスゲーム単位 | サイドアウト制の考慮 |
| コート図 | ソフトテニス用 | テニス用 | ピックルボール用 |

| 分析 | 前衛後衛、ミス、相手ミス | サーブキープ、ブレーク | 3球目、キッチン周り |

## 4. ソフトテニス内の拡張候補

### 4.1 団体戦対応

考え方:

- 1対戦の中に複数試合を持つ
- 1番手、2番手、3番手などを管理する
- 団体戦全体の勝敗を表示する
- 各試合のサマリーをまとめる

必要になりそうなデータ:

- 大会名
- 学校名
- 対戦校
- 何番手か
- 各試合の勝敗
- 団体戦スコア

### 4.2 選手別成長記録

考え方:

- 個人別 `+ / -` を複数試合で見る
- レシーブミス、ダブルフォールト、ストロークミスの推移を見る
- 得意な得点パターンを見る

注意:

- 端末内だけだと長期管理に限界がある
- 本格化するならバックアップやクラウド同期を検討する

### 4.3 次に活かすポイント管理

考え方:

- 試合分析から次に活かすポイントへ変換する
- 例: レシーブミスが多い → レシーブ成功本数練習
- 例: 最初の2本で失点 → 序盤の安全な入り方


### 4.4 大会運営表・Google Driveデータから見えた団体戦要素

Google Drive内の既存表データを確認したところ、ポイント単位の試合記録ではなく、大会運営、組み合わせ、試合結果、コート割に近いデータが見つかった。

団体戦対応では、個人戦の1試合記録だけでなく、以下を別レイヤーとして持つ設計が必要。

- 大会、カテゴリ、会場、コート
- 予選リーグ、順位、勝率、ゲーム差
- 団体戦内の1番手、2番手、3番手
- 団体戦全体の勝敗と各試合結果
- 大会進行表と試合記録の紐づけ

実データをfixture化する場合は、実名や団体名を使わず、完全匿名化した構造データとして作成する。

## 5. AI機能を入れる場合

現状はAIなし。  
AIを入れる場合は、費用、個人情報、通信、責任範囲を慎重に考える。

検討事項:

- API利用料
- 入力データを外部送信するか
- 本名や学校名を送るリスク
- 利用規約、プライバシーポリシー
- 有料化の必要性
- AIコメントの正確性

初期案:

- まずはCSVやサマリーをユーザーが任意で貼り付ける方式にする
- 自動送信はしない
- 匿名化したデータだけ使う
- AIコメントは助言ではなく、振り返り補助として表現する

## 6. 有料化を考える場合

無料でテスト運用するのは妥当。

有料化を考えるタイミング:

- 継続利用者がいる
- チーム単位で使いたい声がある
- AIやクラウドなど運用費が発生する
- サポート対応が必要になる
- データ管理の責任が重くなる

有料化前に必要そうなもの:

- 利用規約
- プライバシーポリシー
- 問い合わせ窓口
- データ削除方法
- バックアップ方法
- 障害時の案内

## 7. 次に作るなら意識すること

- 最初から要件、基本設計、詳細設計、テスト設計を分ける
- 競技ルールを設定ファイル化できるか考える
- UI部品を共通化する
- 分析ロジックを競技別に差し替えられるようにする
- データ保存形式を先に決める
- テストケースを最初から作る
